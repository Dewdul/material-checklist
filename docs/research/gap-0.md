# Gap follow-up: Which recipe-data sourcing model is the plugin actually committing to: the itemids-data agent's hand-written Java dataset (~40-80 recipes as records/enums referencing net.runelite.api.gameval.ItemID), or the genre-standard offline wiki-Bucket-generated bundled JSON (~4,600 recipes, as in KludensVogter/Recipes_Checklist tools/generate_recipes.py)? The two findings recommend opposite approaches, and the product goal 'items from ANY production skill' is incompatible with hand-writing 40-80 recipes. If the generated-JSON route is chosen, nobody has researched the generator mechanics that make it work: the wiki-name-to-item-ID join (Bucket production_json materials carry NAMES only; the join via bucket('infobox_item') must disambiguate multiple IDs per name, e.g. charged/degraded variants), how interchangeable ingredients (recipe-checklist's Ingredient.same list, e.g. watered vs unwatered seedlings, 'any plank') are derived from wiki data, how the 5-variant-per-product problem (Molten glass subtxt variants) is filtered, and how many of the 7,674 Bucket:Recipe rows survive to a usable dataset. Concrete research: read KludensVogter/Recipes_Checklist tools/generate_recipes.py and its recipes.json schema end-to-end. Secondary sub-question nobody touched: OSRS Wiki content is CC BY-NC-SA â€” is bundling wiki-derived recipe JSON inside a BSD-2-Clause hub plugin an accepted practice beyond the single recipe-checklist precedent (attribution requirements, any hub reviewer stance)?

## VERDICT: Commit to the wiki-Bucket-generated bundled JSON model. The hand-written Java dataset is not viable for the stated product goal, and every generator mechanic the JSON route needs is now verified against live sources.

### 1. The contradiction, settled with numbers
Ran KludensVogter/Recipes_Checklist `tools/generate_recipes.py` live against the OSRS Wiki Bucket API on 2026-09-05: **7,682 raw `recipe` bucket rows â†’ 4,867 usable recipes** (skips: 2,032 "no output or materials" = activity/resource-spot/quest-reward boxes; 553 "makes itself" = product listed as own input; 75 "unknown material"; ~155 more collapsed as duplicate signatures or empty-ingredient rows). The bundled snapshot in the repo has 4,653 recipes â€” i.e. **214 recipes of drift in under a month** (Sailing-era content). A hand-written 40â€“80-recipe Java dataset is ~1.6% coverage and cannot track this drift; moreover **87 surviving recipes have `productId: 0`** (buildable scenery â€” POH furniture pre-flatpack forms, ship landing sites, looms) which *cannot be represented* as `net.runelite.api.gameval.ItemID` constants because no item exists. `gameval.ItemID` remains useful in plugin *code* (e.g. `ItemID.COINS`) but is irrelevant to the *dataset*, which carries raw numeric ids. recipe-checklist is a real merged Plugin Hub plugin (`recipe-checklist` in plugin-hub/plugins, PR #14869 merged 2026-08-25, updated via #15435), proving the whole pipeline end-to-end.

### 2. Generator mechanics (read end-to-end, 337 lines, verified by live execution)
`tools/generate_recipes.py` â€” stdlib-only Python (urllib + json + re), no deps. Flow:
- **Bucket API**: `GET https://oldschool.runescape.wiki/api.php?action=bucket&format=json&query=...` with query language `bucket('recipe').select('production_json').limit(2000).offset(N).run()`. Must send a real User-Agent. Pages of 2000 until a short page. Official docs: wiki page "RuneScape:Bucket" (the old SMW `action=ask` API is deprecated in favor of Bucket; bucket list at namespace 9592 / `Bucket:...` pages).
- **`production_json` schema** (verified raw sample): `{ticks, materials:[{name, quantity, image}], facilities, skills:[{name, level, experience, boostable}], members, output:{name, quantity, cost, subtxt, image}}`. **Materials carry NAMES only â€” no item ids.** Note: `skills` (level requirements), `ticks`, `experience` are available but discarded by recipe-checklist; our plugin could keep levels.
- **Nameâ†’ID join**: built from `bucket('infobox_item').select('item_name','item_id')` (16,790 rows live) plus `infobox_construction` and `infobox_ship_part` buckets keyed by `page_name` (without these, every POH build and ship part drops out for having an unresolvable product; their `item_id` is the flatpack/part item, used for icons). `item_id` is a LIST of strings â€” first element is canonical (76 rows have multiple ids, e.g. Puzzle box: 6 ids); values can be non-numeric (`"interface8283"`) so int() must be guarded. Index built with `dict.setdefault(name.lower(), first_id)` â†’ **first bucket row wins**. Live measurement: 11,504 distinct lowercase names, of which **1,273 map to >1 distinct candidate id** â€” resolved purely by bucket return order (canonical/older pages come first, so e.g. "Coins" resolves to 995 not 617/6964/8890 â€” verified correct in both bundled and freshly generated output). This is the fragile heuristic; cheap CI assertion of known ids recommended.
- **Name cleaning**: strip `[[link|label]]` markup; split on `#` (page anchors like "Bow of faerdhinen#Inactive" â€” part before # is the item, anchor kept as variant label); `resolve()` retries up to 3 times stripping trailing ` (qualifier)` â€” so page "Crystal crown (Ithell)" â†’ item "Crystal crown"; the regex requires a space before "(" so "Prayer potion(4)" stays intact.
- **Quantities are free text** ("1", "2-3", "0.5", "Varies"): takes the LOW end of ranges, `max(1, round(float))`, rejects unparseable â†’ whole recipe dropped rather than guessed.
- **The 5-variant Molten glass problem is NOT filtered â€” it's named**: all 5 variants survive as separate recipes ("Molten glass (Normal furnace)", "(Superglass Make - giant seaweed)" etc.), disambiguated via `output.subtxt`, falling back to page anchor, then `facilities`, then the ingredient not shared by all variants (`name_variants()` computes the shared-ingredient intersection). Exact duplicates are collapsed by signature `(product_id, makes, sorted((itemId,qty)))` â€” e.g. furnace vs blast furnace when materials are identical. Name collisions get a "(2)" suffix as last resort because **recipe name is the plugin's primary key**. Choosing among variants is a LOOKUP-time concern: `RecipeBook.simplestFor(int)` picks fewest ingredient kinds, ties broken toward MORE raw material (so blast-furnace half-coal doesn't understate a shopping list), then shorter name.
- **`Ingredient.same` is NOT a general interchangeability system**: it is generated ONLY for the 24 watered saplings â€” `build_watered_aliases()` maps every item named `X (w)` to item `X`; recipes reference the unwatered id and `same:[watered_id]` makes held watered ones count. **"Any plank" does not exist in wiki data** â€” construction recipes name concrete planks per variant (Oak larder = 8Ã—8778). Broader interchangeability ("any raw fish â†’ fish offcuts") appears as separate recipe VARIANTS, not merged alternatives. If Material Checklist wants richer alternative-groups, that's hand-curated data layered on top.
- **Batch yields**: `makes` (667 recipes, e.g. bronze bar â†’ 15 nails, Superglass Make 3 giant seaweed+18 sand â†’ makes:29); `Recipe.batchesFor(wanted)` does ceiling division.

### 3. Consuming schema (verified in shipped Java)
`recipes.json` (858 KB, at `src/main/resources/com/recipechecklist/recipes.json`, loaded via `RecipeBook.class.getResourceAsStream("recipes.json")` with RuneLite's **injected** `Gson` and a `TypeToken<List<Recipe>>`): entries are `{name, productId, ingredients:[{itemId, quantity, same?:[int]}], makes?}` â€” exactly 4 top-level keys, 3 ingredient keys, nothing else. Material display names come from the game cache at runtime (`itemManager.getItemComposition(id).getName()`), icons via `itemManager.getImage(id)`, and container counting canonicalizes (`itemManager.canonicalize(item.getId())`) so noted/placeholder variants merge â€” this is also what makes the wiki's canonical-id choice line up with bank contents. All ItemManager signatures verified against current runelite master: `getItemComposition(int)` L459, `canonicalize(int)` L467, `getImage(int)` L522, `getImage(int,int,boolean)` L538.

### 4. Licensing sub-question: bundling CC BY-NC-SA wiki data in a BSD-2-Clause hub plugin IS accepted practice, with attribution
- OSRS Wiki content is **CC BY-NC-SA 3.0** (RuneScape:Copyrights; "Content on this site is licensed under CC BY-NC-SA 3.0").
- **Precedent beyond recipe-checklist exists and predates it by 6 years**: shortest-path (hub PR #707, Oct 2020, one of the most-installed hub plugins) bundled wiki-derived `transports.txt`; during review the author told reviewer Nightfirecat: "transports.txt is from the RS wiki data, licensed under CC BY-NC-SA 3.0 (same as rest of the wiki content). I added attribution in the readme and the top of that file" â€” and it was merged. So the hub-reviewer-visible norm is: **wiki data + README/file attribution = fine**; nobody demands the data file be separately CC-licensed.
- recipe-checklist itself (BSD-2-Clause, merged 2026-08-25, PR #14869) attributes via README ("~4,600 recipes generated from the OSRS Wiki") with zero public reviewer objection.
- A second same-genre plugin merged 2026-08-27: **required-materials** (SchauweM/runelite-required-materials, hub PR #15145) â€” tracks Sailing/Construction build materials but fetches each item's wiki page **at runtime** through RuneLite's injected OkHttpClient and parses the `{{Recipe}}` template, caching per session. So the hub accepts BOTH sourcing models; bundled-offline matches our spec better (works offline, zero latency, no per-user wiki load; recipe-checklist README: "The plugin never makes a network request; the data is baked in at build time").
- The hub README imposes only "BSD 2-Clause" repo licensing; there is no written third-party-data policy â€” the stance above is established review practice. Recommendation: BSD-2-Clause repo + a README "Recipe data" section crediting the OSRS Wiki under CC BY-NC-SA 3.0 with a link, mirroring both precedents. NC is unproblematic (RuneLite hub plugins are free, no monetization).

## Risks
- First-row-wins name join is order-dependent: 1,273 of 11,504 item names have multiple candidate ids and are resolved only by bucket page order (canonical pages happen to be older and returned first - 'Coins'->995 verified correct, but nothing guarantees this for future pages). Mitigate with a CI spot-check of known ids after every regeneration.
- Dataset drift is fast (~214 new recipes between the bundled Aug-2026 snapshot and 2026-09-05, Sailing era): the JSON must be regenerated per release or totals silently go stale for new content; the generator has no version/date stamp in its output - consider adding one.
- CC BY-NC-SA ShareAlike technically means the derived recipes.json should itself carry CC BY-NC-SA rather than the repo's BSD-2-Clause; hub practice (shortest-path #707, recipe-checklist #14869) treats a README attribution as sufficient and no reviewer has objected, but this is review custom, not written policy - a future reviewer could ask for a data-file license header (JSON cannot hold comments, so put the notice in README and/or a sidecar file).
- The generator silently drops rows in ways not visible in skip counters (empty-ingredient rows and duplicate signatures, ~155 live); 553 'makes itself' skips include some legitimate charging/refill recipes a user might search for and not find.
- Interchangeability is nearly absent from wiki data: only 24 watered-sapling 'same' aliases exist; 'any plank'/'any log' style requirements surface as separate recipe variants, so aggregate raw-material math can overstate needs when a player would mix material types; richer alternative-groups would be hand-curated additions the wiki cannot generate.
- production_json quantities are free text and the generator takes the LOW end of ranges - for 'Varies' recipes (dropped) and range recipes the checklist can understate or omit; acceptable for v1 but worth knowing.
- Bucket API is comparatively new (successor to the deprecated SMW ask API) and its query surface or bucket schemas could change; the generator is dev-time-only so breakage never affects shipped users, but pin expectations with the row-count sanity check.
- 87 productId=0 recipes need UI care (no product icon - recipe-checklist falls back to first ingredient's icon) and cannot be keyed by item id anywhere in persistence - name is the only stable key, which is why the generator enforces name uniqueness; any Material Checklist persistence design must key goals by recipe NAME, not product id.
- required-materials (merged 2026-08-27) proves a runtime-fetch alternative is also hub-acceptable, but it depends on wiki availability/latency and parses {{Recipe}} wikitext per click; do not mix models - bundled JSON was chosen precisely to avoid network requests from the client.

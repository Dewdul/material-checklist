# Research: itemids-data

# Item IDs and recipe/materials data â€” research findings (verified against runelite/runelite master, 2026-09-05)

## 1. Item ID constants: gameval is current, old ItemID is deprecated

- **`net.runelite.api.ItemID` (runelite-api) is `@Deprecated`.** Verified from raw source: class-level javadoc is `/** @deprecated Use {@link net.runelite.api.gameval.ItemID} */` with `@Deprecated @SuppressWarnings("unused") public final class ItemID`. It uses wiki-style names (`DWARF_REMAINS = 0`, `TOOLKIT = 1`). It is legacy/frozen; do not use it in new code â€” hub reviewers now expect gameval.
- **`net.runelite.api.gameval.ItemID` is the current class.** Header: `/* This file is automatically generated. Do not edit. */`, `package net.runelite.api.gameval;`, `@SuppressWarnings("unused") public final class ItemID`. The file is 104,667 lines. Constant names are derived from **Jagex internal cache names**, with a javadoc line above each constant giving the in-game display name, e.g. `/** Dwarf remains */ public static final int MCANNONREMAINS = 0;`.
- Names are often intuitive (`MOLTEN_GLASS = 1775`, `BOW_STRING = 1777`, `SODA_ASH = 1781`, `FLAX = 1779`, `LEATHER = 1741`, `COINS = 995`, `BRONZE_BAR = 2349`, `IRON_BAR = 2351`, `STEEL_BAR = 2353`, `VIAL_WATER = 227`, `VIAL_EMPTY = 229`, `UNSTRUNG_LONGBOW = 48`, `UNSTRUNG_YEW_LONGBOW = 66`, `UNSTRUNG_GOLD_AMULET = 1673`, `BUCKET_SAND = 1783` for "Bucket of sand") but frequently **differ from wiki names and can be cryptic**: `BRONZECRAFTWIRE` (Bronze wire), `NAILS_BRONZE`, `XBOWS_CROSSBOW_BOLTS_BRONZE_UNFEATHERED` (Bronze bolts (unf)), `BRUT_BRONZE_SPEAR` (Bronze hasta), `SPIT_IRON`, `CAMDOZAAL_BARRONITE_DEPOSIT`, `SAILING_BOAT_KEEL_PART_BRONZE`. IDE autocomplete + the javadoc display names are the intended discovery mechanism.
- gameval `ItemID` contains **nested classes**: `ItemID.Cert` (line 90043 â€” noted variants, e.g. `Cert.BRONZE_BAR = 2350`, `Cert.VIAL_WATER = 228`) and `ItemID.Placeholder` (line 94763 â€” bank placeholders, e.g. `Placeholder.BRONZE_BAR = 13885`). Use canonical IDs for recipes; un-note/un-placeholder owned items via `ItemManager.canonicalize(int)`.
- The full gameval package on master: `AnimationID, DBTableID, InterfaceID, InventoryID, ItemID, NpcID, ObjectID, ObjectID1, SpotanimID, SpriteID, VarClientID, VarPlayerID, VarbitID` (ObjectID is split into ObjectID/ObjectID1 for size).
- Relevant sibling: `net.runelite.api.gameval.InventoryID` is a class of int constants â€” `InventoryID.INV = 93`, `InventoryID.BANK = 95` â€” while the old `net.runelite.api.InventoryID` **enum** is `@Deprecated` (verified both files).

## 2. How the core skill calculator bundles data (the ecosystem-standard pattern)

Location: `runelite-client/src/main/java/net/runelite/client/plugins/skillcalculator/` (`CalculatorType`, `SkillCalculator`, `SkillCalculatorPanel`, `SkillCalculatorPlugin`, `UIActionSlot`, `UICalculatorInputArea`, `UICombinedActionSlot`) plus `skills/` subpackage.

- Data is **hand-written Java enums, not JSON**. Per skill: `AgilityAction, ConstructionAction, CookingAction, CraftingAction, FarmingAction, FiremakingAction, FishingAction, FletchingAction, HerbloreAction, HunterAction, MagicAction, MiningAction, PrayerAction, RunecraftAction, SailingAction, SmithingAction, ThievingAction, WoodcuttingAction` (+ `*Bonus` enums). Note `SailingAction` exists â€” Sailing is a live skill; our plugin should include it.
- Pattern (verified in SmithingAction raw source): `@AllArgsConstructor @Getter public enum SmithingAction implements ItemSkillAction { BRONZE_BAR(ItemID.BRONZE_BAR, 1, 6.2f), ... }` with `import net.runelite.api.gameval.ItemID;`. Fields: `int itemId, int level, float xp` (+ optional `boolean isMembersOverride` in some enums).
- Interfaces: `ItemSkillAction extends SkillAction` with `int getItemId()`, `default int getIcon() { return getItemId(); }`, `default String getName(ItemManager im)` â†’ `im.getItemComposition(getItemId()).getMembersName()`, `default boolean isMembers(ItemManager im)` â†’ `im.getItemComposition(getItemId()).isMembers()`. Wiring: `CalculatorType` enum, e.g. `SMITHING(Skill.SMITHING, SmithingBonus.values(), SmithingAction.values())`, `CRAFTING(Skill.CRAFTING, null, CraftingAction.values())`.
- **Critical gap: the skill calculator stores only product + level + xp. It has NO materials/ingredients data.** RuneLite core contains no recipe dataset we can reuse; we must author our own materials data.
- Core client precedent for bundling *generated* JSON: `net.runelite.client.game.ItemVariationMapping` loads `/item_variations.json` from classpath resources in a static initializer via `getResourceAsStream` + Gson `TypeToken<Map<String, Collection<Integer>>>`; exposes static `int map(int itemId)` (variationâ†’base) and `Collection<Integer> getVariations(int base)` â€” also directly useful to us for lumping item variants when counting owned materials.

## 3. Machine-readable OSRS recipe datasets (2026 state)

- **OSRS Wiki "Bucket" API is the live, structured recipe source.** The wiki migrated off Semantic MediaWiki (`action=ask` deprecated) to the weirdgloop **Bucket** extension. Endpoint: `https://oldschool.runescape.wiki/api.php?action=bucket&format=json&query=<lua-ish query>`. **`Bucket:Recipe` exists with 7,674 recipe rows.** Fields: `uses_material` (repeated PAGE), `uses_tool`, `uses_facility`, `uses_skill`, `is_members_only`, `is_boostable`, `source_template`, `production_json` (TEXT, unindexed). Recipes attach to the *output item's page* (`page_name`).
- Live-verified query and response shape (Molten glass returned 5 recipe variants â€” normal furnace + 4 Superglass Make flux variants, distinguished by `output.subtxt`): `production_json = { "ticks":"2", "materials":[{"quantity":"1","name":"Bucket of sand","image":"..."},{"quantity":"1","name":"Soda ash",...}], "facilities":"Furnace", "skills":[{"experience":"20","level":"1","name":"Crafting","boostable":""}], "members":true, "output":{"cost":89,"quantity":"1","name":"Molten glass","subtxt":"Normal furnace","image":"..."} }`. Materials are **wiki item names, not item IDs** â€” an ID join is needed via `bucket('infobox_item').select('item_id','item_name')...` or the prices mapping endpoint. Wiki template feeding this: `Template:Recipe` / `Module:Recipe` (params `mat#`, `mat#quantity`, `skill#`, `skill#lvl`, `skill#exp`, `output#`, `output#quantity`, `ticks`, `tools`, `facilities`, `members`).
- **osrsbox-db is dead** â€” last push 2022-08-07 (GitHub API). Fork `0xNeffarion/osrsreboxed-db` last push 2025-01-07, i.e. ~20 months stale by Sep 2026. Neither should be a dependency; osrsbox item JSON never carried recipes anyway.
- **static.runelite.net has no recipe data.** It serves `https://static.runelite.net/item/stats.ids.min.json` (`Map<Integer, ItemStats>` â€” equipment/combat stats), config.json, jav_config backup, apidocs. Not a recipe source.

## 4. Item price API

- `net.runelite.client.game.ItemManager` (`@Singleton`, constructor-`@Inject`ed with Client, ScheduledExecutorService, ClientThread, EventBus, ItemClient, RuneLiteConfig). Key methods (verified via source + published apidocs at static.runelite.net/runelite-client/apidocs): `int getItemPrice(int itemID)`; `int getItemPriceWithSource(int itemID, boolean useWikiPrice)`; `int getWikiPrice(net.runelite.http.api.item.ItemPrice)` ("with checks to try and avoid excessive price manipulation"); `int canonicalize(int itemID)` ("un-noted, un-placeholdered ID"); `@Nonnull ItemComposition getItemComposition(int itemId)`; `List<ItemPrice> search(String itemName)`; `AsyncBufferedImage getImage(int itemId)` / `getImage(int itemId, int quantity, boolean stackable)`; `BufferedImage getItemOutline(int, int, Color)`; `ItemStats getItemStats(int itemId)`.
- Price plumbing: `net.runelite.client.game.ItemClient.getPrices()` GETs `{runelite.api.base}/item/prices.js` â†’ `ItemPrice[]`; `getStats()` GETs `{runelite.static.base}/item/stats.ids.min.json`. From `runelite-client/src/main/resources/net/runelite/client/runelite.properties`: `runelite.api.base=https://api.runelite.net/runelite-${project.version}` and `runelite.static.base=https://static.runelite.net`. Live sample against client 1.12.38 (current per static.runelite.net/bootstrap.json): `[{"id":2,"name":"Steel cannonball","price":243,"wikiPrice":243},...]` (~322 KB, tradeable items only). ItemManager refreshes prices on a 30-minute scheduled task and caches in an immutable map; noted items resolve via `getLinkedNoteId()`, worn/broken variants via an internal `WORN_ITEMS` map, untradeables via `net.runelite.client.game.ItemMapping.map()` (decomposes to tradeable components), placeholders via `canonicalize()`. Untradeable/unknown items price as 0.
- `ItemPrice` type is `net.runelite.http.api.item.ItemPrice` (fields per payload: `id`, `name`, `price` (GE), `wikiPrice`). The http-api module is no longer in the main repo â€” it is an external frozen artifact `net.runelite:http-api` (latest 1.8.7.1) on repo.runelite.net; the main repo is now **Gradle** (`build.gradle.kts`, version catalog `libs.rl.http.api`). For a plugin this is transparent: it's a transitive dep of `net.runelite:client`.
- Direct wiki price API (only if we need build-time data; in-client, use ItemManager): `https://prices.runescape.wiki/api/v1/osrs/latest?id=1775` â†’ `{"data":{"1775":{"high":81,"highTime":...,"low":78,"lowTime":...}}}`; `/api/v1/osrs/mapping` â†’ `[{id,name,examine,members,value,lowalch,highalch,limit,icon}]` (note `limit` = GE buy limit â€” useful for a shopping list). Descriptive User-Agent required by wiki policy.

## 5. Hub bundling practice + plugin-hub constraints

- Dominant hub pattern for static game data = **Java code referencing gameval constants**. Quest Helper (largest hub plugin, Zoinkwiz/quest-helper) uses `import net.runelite.api.gameval.ItemID;` with `ImmutableList<Integer>` collections of constants (verified `com/questhelper/collections/ItemCollections.java`); an April 2025 hub PR wave "update deprecated usages to use gameval" shows the ecosystem migrated.
- Plugin-hub rules (README, verified): resources may live in `src/main/resources` but MUST be read with `Class.getResourceAsStream(...)` â€” the jar is never unpacked, `getResource()` file-URL assumptions break in production. Any dependency that is not a transitive dep of runelite-client requires Gradle dependency-verification sha256 metadata plus manual maintainer review ("adds significantly to review time... avoid adding any new dependencies unless absolutely necessary") â€” so use Gson/Guava/OkHttp from runelite-client transitively, add nothing new. Template: `runelite/example-plugin` â€” repos `mavenLocal()`, `https://repo.runelite.net` (net.runelite.* only), `mavenCentral()`; deps `compileOnly 'net.runelite:client:latest.release'`, `compileOnly+annotationProcessor 'org.projectlombok:lombok:1.18.30'`, `testImplementation 'junit:junit:4.12'` and `testImplementation net.runelite:jshell latest.release`; Java 11 target.

## 6. Assessment: safest representation for ~40-80 hand-written recipes

**Recommendation: hand-write recipes in Java referencing `net.runelite.api.gameval.ItemID` constants (skill-calculator style enum, or a static `List<Recipe>` built with a small builder), NOT raw ints in JSON.**

Rationale:
1. Compile-time safety: a typo'd constant fails the build; a typo'd raw int in JSON ships silently. gameval names are cryptic enough (`BRONZECRAFTWIRE`, `BRUT_BRONZE_SPEAR`, `XBOWS_CROSSBOW_BOLTS_BRONZE_UNFEATHERED`) that IDE autocomplete + per-constant javadoc display names are the practical defense against wrong IDs; raw ints get neither.
2. It matches core (`SmithingAction` et al.) and flagship hub practice (Quest Helper), so hub reviewers recognize the pattern.
3. `public static final int` constants are inlined at compile time â€” zero runtime cost, no reflection, no resource-loading edge cases.
4. JSON would additionally need a nameâ†’id build step or hand-maintained ints, plus getResourceAsStream handling; for 40-80 recipes the enum is less total machinery.

Suggested shape (marries skillcalculator conventions with our materials need): `enum/record Recipe { int productId; Skill skill; int level; float xp; int outputQuantity; Ingredient[] ingredients; }` with `record Ingredient(int itemId, int quantity)`; intermediates (e.g. `ItemID.MOLTEN_GLASS`, `ItemID.UNSTRUNG_YEW_LONGBOW`) recurse simply because their product id appears as another recipe's product â€” resolve recursively at aggregation time, guard against cycles with a unit test asserting the recipe graph is a DAG. Add JUnit tests asserting: unique product ids per variant, all quantities > 0, and every ingredient id either terminal or itself a recipe product.

Two hygiene points: (a) gameval is auto-generated from Jagex internal names â€” a Jagex rename changes the *constant name* (int value stays stable); failure mode is a compile error on client upgrade, which is the safe direction; example-plugin builds against `latest.release`, so a rename surfaces immediately. (b) Use canonical (un-noted) ids in recipes and run owned-item counts through `ItemManager.canonicalize(int)`; consider `ItemVariationMapping.map(int)` when counting owned materials so cosmetic/state variants collapse to the base item.

Optional build-time cross-check (not a runtime dependency): a dev script querying the wiki Bucket API (`bucket('recipe')...where('page_name', <product>)`) to diff our hand-written quantities/levels against `production_json`, with namesâ†’ids joined via the prices `/mapping` endpoint. Good CI validation; too messy (multi-variant `subtxt`, name mismatches, unindexed field) to be the primary source.

## Risks
- gameval constant NAMES are auto-generated from Jagex internal names and can be renamed between client releases (int values stay stable); building against net.runelite:client:latest.release means a rename shows up as a compile error â€” safe but can break CI without any code change on our side.
- The exact xp/level floats quoted from CraftingAction and the old-ItemID constant names came from an LLM-summarized fetch rather than direct grep; treat those specific numbers as approximate and re-verify per-recipe values when authoring data (all gameval names/values and SmithingAction lines quoted above were verified by direct grep of raw source).
- Bucket production_json materials use wiki display names, the field is unindexed (can only be fetched per page_name, not searched by material), and many outputs have multiple recipe variants distinguished only by output.subtxt (e.g. 'Normal furnace' vs Superglass Make) â€” automated ingestion needs per-variant disambiguation and a name->id join; use it for CI cross-validation, not as the primary data source.
- The Bucket API replaced SMW recently and is documented as evolving (meta.weirdgloop.org Extension:Bucket/Api); query syntax or bucket schemas could shift â€” pin the dev-script queries and expect maintenance.
- osrsbox-db is dead (2022) and osrsreboxed-db stale (Jan 2025); item IDs added after their last updates (including all Sailing content) are missing there â€” avoid entirely.
- api.runelite.net price endpoints are versioned per client release (runelite-${version}/item/prices.js) and are not a stable third-party contract; inside the plugin always go through ItemManager rather than HTTP.
- Plugin-hub review discourages new third-party dependencies (sha256 verification + manual maintainer review adds significant review time) â€” stick to Gson/Guava/OkHttp already provided transitively by runelite-client.
- ItemManager.getItemPrice returns 0 for untradeables (e.g. some intermediates like quest-locked items) and coins/wiki prices can differ from GE 'price' vs 'wikiPrice' â€” decide explicitly which source (getItemPriceWithSource useWikiPrice) the Raw Materials cost column uses.

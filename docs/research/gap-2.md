# Gap follow-up: Where should the persisted bank snapshot live, and is ConfigManager (especially RSProfile config) safe for a multi-kilobyte blob? The containers agent recommends setRSProfileConfiguration("materialchecklist", "bankSnapshot", json) â€” but NONE of the surveyed hub plugins use RSProfile config for bank snapshots: recipe-checklist writes a JSON file to new File(RuneLite.RUNELITE_DIR, "recipe-checklist")/bank-<accountHash>.json, bank-memory and goal-tracker use plain (non-RSProfile) config keys with manual account-hash keying and compact CSV-style serialization to reduce bloat. Unverified specifics: (a) whether RuneLite's config profiles (which sync to the runelite.net cloud when the user enables cloud profiles) impose or informally discourage size limits on config values â€” a maxed bank snapshot is roughly 800-1,200 id,qty pairs, i.e. 10-25 KB of JSON per RS profile; (b) whether hub reviewers flag large config blobs (AGENTS.md, verified 2026-09-05, is silent on both config sizing and RSProfile usage); (c) whether RSProfile keys are included in cloud profile sync and what happens on conflict across machines. Concrete research: inspect ConfigManager/ConfigClient sync code paths on runelite master for size handling, and search plugin-hub PR review comments for precedent on large config values vs RUNELITE_DIR files.

## VERDICT: RSProfile config is safe, and it is the MAINSTREAM pattern â€” the surveyed hub plugins are the outliers, not the incumbents

The premise that "none of the incumbents use RSProfile config for bank snapshots" is falsified by the two most authoritative precedents:

1. **RuneLite core's own Loot Tracker** (`runelite-client/.../plugins/loottracker/LootTrackerPlugin.java`, master) stores unbounded per-account loot JSON in RSProfile config: `profileKey = configManager.getRSProfileKey()`, then `configManager.setConfiguration(LootTrackerConfig.GROUP, profileKey, "drops_" + type + "_" + name, json)` â€” chunked per kill-source, gson JSON values, enumerated back via `getRSProfileConfigurationKeys(GROUP, profileKey, "drops_")`. This is first-party code shipping to every user.
2. **Dude, Where's My Stuff** (the actively-maintained hub plugin that superseded bank-memory â€” bank-memory's own takeover PR runelite/plugin-hub#11123 was closed in March 2026 with the would-be maintainer told to just use DWMS) stores its ENTIRE storage state (bank + ~20 other containers) in RSProfile config: `Storage.save()` calls `configManager.setConfiguration(CONFIG_GROUP, profileKey, key, saveString)` with `profileKey = configManager.getRSProfileKey()`, compact `;`/`,`-joined `id,qty` save strings (SaveFieldFormatter), and a `lastSaveString` equality check to skip redundant writes.
3. **Current hub review practice actively prefers config over files.** In plugin-hub PR #12366 (Waypointer, June 2026, merged), runelite org MEMBER riktenx wrote: "file i/o will make your plugin require manually review. if you can not use it your plugin can be automatically reviewed... it seems like if you're just saving paths it should be possible to do so in config". The author then moved everything into `setRSProfileConfiguration` ("same approach as ground markers / loot tracker") and the PR merged. So recipe-checklist's RUNELITE_DIR file is the pattern that CAUSES review friction (manual review on every update), not the one that avoids it.

## Size limits (question a)

- **Client side: no size limits whatsoever.** `ConfigManager.setConfiguration` validates only key format (`Strings.isNullOrEmpty(groupName/key)`, no `:` in key, no leading `$` â€” throws IllegalArgumentException). Storage is a `ConcurrentHashMap<String,String>` flushed to a Java `.properties` file (UTF-8, atomic temp-file + `FileChannel.lock()` + `ATOMIC_MOVE` in `ConfigData.patch()`). No truncation anywhere.
- **Server side (historical, last public source):** `http-service/.../config/ConfigService.java` at tag `runelite-parent-1.6.0` enforced `MAX_VALUE_LENGTH = 262144` chars (256 KiB) per value and JSON nesting depth â‰¤ 8, MongoDB-backed. The current `config/v3` service is closed-source (http-service removed from the repo; 404 on master), but a 10â€“25 KB snapshot is ~1/10th of even the old per-value cap, and Loot Tracker's `drops_*` values are comparably large in practice. The v3 client handles per-value rejection ("failed to synchronize some of {edit}/{unset} configuration values" warn in `ConfigClient.patch` on non-200) â€” evidence the server validates per-patch, and no GitHub issues surfaced showing users hitting size rejections.
- **Hub reviewers (question b):** no PR comments found flagging large config values (searched `in:comments` for "large config", "setRSProfileConfiguration", "profile config", RUNELITE_DIR, etc.); the only on-point maintainer guidance found (PR #12366) pushes AWAY from files and TOWARD config. AGENTS.md silence is consistent with this: config is the default, files are the exception needing scrutiny.

## Cloud sync & conflict semantics (question c) â€” verified line-by-line on master ConfigManager.java

- The `$rsprofile` internal profile (name `"$rsprofile"`, fixed id `-1L`) is unconditionally `setSync(true)` at load (lines 546â€“548) and in `migrate()` (line 366). **RSProfile keys DO sync to the runelite.net cloud â€” but only when the user is signed into a runelite.net account**: `saveConfiguration` gates the network patch on `profile.isSync() && sessionManager.getAccountSession() != null`. No account = purely local file, zero cloud involvement.
- Local file: `RUNELITE_DIR/profiles2/$rsprofile--1.properties` (`ProfileManager.profileConfigFile` = `PROFILES_DIR, name + "-" + id + ".properties"`).
- Sync cadence: `scheduledExecutorService.scheduleWithFixedDelay(this::sendConfig, 30 + rand(300), 300, SECONDS)` â€” every 5 min â€” plus on `ClientShutdown` (@Subscribe priority -100, after plugins) and profile switches. Patches are key-level diffs (`ConfigPatch{edit: Map, unset: List}`) sent as HTTP PATCH to `config/v3/{profileId}` with `RUNELITE_AUTH` header.
- Conflict model: **key-level last-writer-wins merge**. On `SessionOpen`, the ENTIRE local `$rsprofile` is PATCHed into remote first â€” code comment (lines 268â€“271): "$rsprofile ... acts as an automatically-synced profile that is always merged instead of overwritten. After a login send a PATCH for the offline $rsprofile to merge it ... so that when $rsprofile is synced later it doesn't overwrite and lose the local $rsprofile settings." On startup rev mismatch, `syncRemote` does `configFile.delete()` and rewrites local from remote (remote replaces local wholesale).
- **Real data-loss vector found (matches the "silent loss" worry, but it's not size-specific):** if a cloud PATCH fails or returns non-200, `ConfigClient` completes the future null â†’ `saveConfiguration` sets `profile.setRev(-1L)` â†’ next startup `syncRemote` sees rev mismatch and replaces the local file with remote â€” any local-only values from the failed patch are lost. Mitigation is keeping values well under limits (we are) and chunking.
- **Second silent-drop path:** `setRSProfileConfiguration` while not logged into the game (no resolvable rsProfileKey / no local player) just `log.warn("trying to create a profile while not logged in"); return;` â€” the write is dropped. Bank snapshot writes should happen only on bank `ItemContainerChanged` (which only fires logged in), so this is naturally avoided.

## Recommendation for Material Checklist

Use `configManager.setRSProfileConfiguration("materialchecklist", "bankSnapshot", value)` â€” it matches core (Loot Tracker), the dominant maintained bank tracker (DWMS), and current hub reviewer preference; a RUNELITE_DIR file would force manual review on every release. Adopt the incumbents' hygiene: (1) compact serialization (DWMS-style `id,qty` CSV ~8â€“15 KB for a maxed bank, not pretty-printed JSON); (2) skip writes when unchanged (ConfigManager already no-ops on equal values via `Objects.equals(oldValue, value)` early-return, but comparing before serializing saves work); (3) write only from bank-open/ItemContainerChanged while logged in; (4) optionally chunk if the value grows (loot tracker chunks per source, ground markers per region) â€” a single â‰¤25 KB key is fine at 1/10 the historical server cap. Non-RSProfile config with manual accountHash keying (bank-memory/goal-tracker) is strictly worse: same sync behavior for the shared profile, but hand-rolled keying and pollution of the user's named profile; those plugins predate or ignore the rsProfile API rather than avoid it for a known reason.

## Risks
- The current config/v3 server is closed-source, so the 256 KiB/value limit is only verified for the last public server (runelite-parent-1.6.0, config v2 era); v3 could differ. The client's 'failed to synchronize some of X/Y configuration values' warn path proves per-patch server validation exists. Keep the snapshot compact (CSV, ~8-15 KB) and this is a non-issue at 10x margin
- If a cloud patch IS ever rejected (oversize or otherwise), the failure mode is nasty: rev set to -1, and on next startup the remote profile wholesale replaces the local $rsprofile file (configFile.delete() in syncRemote) â€” the rejected local-only key is silently lost. This is the strongest argument for compact values and for treating the snapshot as a cache (re-derivable next bank visit), never as the only copy of user-authored data. The user's planned-items list is user-authored â€” keep THAT small or in non-RSProfile config; the bank snapshot itself is regenerated on every bank open so loss is self-healing
- setRSProfileConfiguration silently drops writes (log.warn only) when no RS profile key is resolvable (not logged into the game). Only persist from ItemContainerChanged for the bank container (fires only while logged in), and never from shutDown() after logout
- Cross-machine conflict is per-key last-writer-wins over the whole value: two machines alternating on the same account each overwrite the full snapshot key. For a bank snapshot this is correct (the game is the source of truth; newest write is freshest), but do not design multi-key invariants that must update atomically across machines â€” the merge is per-key, not transactional
- Every RSProfile write rides the shared $rsprofile profile synced for ALL plugins; a changed 15 KB value re-uploads in full in the next 5-minute patch cycle. Bank snapshots change only on bank visits, and setConfiguration no-ops on unchanged values, so steady-state cost is zero â€” but avoid rewriting the value every game tick or serializing nondeterministically (e.g., unordered HashMap iteration produces spuriously 'changed' strings; sort by item id before joining)
- GitHub issue/PR comment search does not index all comments and review threads; absence of negative size precedent is suggestive, not proof. The positive precedent (riktenx's merged guidance in plugin-hub PR #12366, core Loot Tracker, DWMS) is the load-bearing evidence
- bank-memory's dedicated write-queue thread and recipe-checklist's RUNELITE_DIR file are NOT evidence of known RSProfile dangers: bank-memory (2020-era, now effectively abandoned â€” its 2026 takeover PR closed in favor of DWMS) predates polished rsProfile APIs, and recipe-checklist's file approach is the one current maintainers say forces manual review. The 'incumbents know something' smell dissolves on inspection
- Config values are strings in a Java .properties file; avoid characters that Properties escapes heavily (newlines, unicode) â€” a compact single-line CSV both minimizes size and avoids escape bloat (properties escaping can roughly double naive JSON with lots of quotes/backslashes is not an issue, but multi-line pretty JSON would be)

# Research: events-config

# RuneLite Plugin Lifecycle, Events, and Config Persistence â€” verified against GitHub master (2026-09-05)

## 1. @PluginDescriptor (net.runelite.client.plugins.PluginDescriptor)
Fields (verified from master source): `String name` (required); `String configName` default "" (internal config name); `String description` default "" ("short, one-line summary"); `String[] tags` default {} ("no spaces, fully lowercase", used with name in plugin search); `String[] conflicts` default {}; `boolean enabledByDefault` default true â€” javadoc explicitly says **"Plugin-Hub plugins should always have this set to true (the default)"** because off-by-default forces users to install then separately enable; `boolean hidden` default false; `boolean developerPlugin` default false; `boolean loadInSafeMode` default true.

## 2. Plugin base class (net.runelite.client.plugins.Plugin)
`public abstract class Plugin implements Module` (Guice Module; `configure(Binder)` empty, overridable). Lifecycle hooks: `protected void startUp() throws Exception`, `protected void shutDown() throws Exception`, plus `public void resetConfiguration()` (called when user resets plugin config). `hashCode`/`equals` are final. The EventBus auto-registers/unregisters the plugin instance around startUp/shutDown, so @Subscribe methods **in the plugin class** need no manual register; anything else (overlays, nav buttons, extra EventBus subscribers, keybind listeners) must be registered in startUp and symmetrically unregistered in shutDown â€” plugins can be toggled at runtime, so shutDown must fully undo startUp. Wiki Developer-Guide: "Overlays must be registered with the overlay manager on plugin startUp, and unregistered on shutDown."

Standard startUp/shutDown responsibilities for a panel plugin: build `PluginPanel`, create `NavigationButton.builder().tooltip(...).icon(BufferedImage).priority(int).panel(pluginPanel).build()`, then `clientToolbar.addNavigation(navButton)`; in shutDown call `clientToolbar.removeNavigation(navButton)` and `overlayManager.remove(overlay)`. `ClientToolbar` (net.runelite.client.ui, @Singleton) methods: `addNavigation(NavigationButton)`, `removeNavigation(NavigationButton)` (both internally wrap SwingUtilities.invokeLater, so callable from any thread), `openPanel(NavigationButton)` (must be on EDT). `NavigationButton` is @Value @Builder with fields: `BufferedImage icon`, `String tooltip` (default ""), `Runnable onClick`, `PluginPanel panel`, `int priority` (lower = earlier in sidebar), `Map<String,Runnable> popup`.

## 3. Events (net.runelite.client.eventbus)
`@Subscribe`: method annotation, `float priority() default 0` ("Higher priorities run first"). EventBus discovery rules (enforced at register time): method must be void, exactly one concrete-class parameter, non-static, and **named "on" + ParameterClassName** (e.g. `onItemContainerChanged(ItemContainerChanged e)`); implemented via LambdaMetafactory. EventBus public API: `synchronized void register(Object)`, `synchronized <T> Subscriber register(Class<T>, Consumer<T>, float priority)`, `synchronized void unregister(Object)`, `unregister(Subscriber)`, `void post(Object event)`. Game events are posted on the **client thread**; do Swing work from handlers via SwingUtilities.invokeLater.

Events we need:
- `GameStateChanged` (net.runelite.api.events) â€” check `getGameState() == GameState.LOGGED_IN` (example-plugin does exactly this). Use it to trigger initial inventory read / panel refresh.
- `ItemContainerChanged` (net.runelite.api.events, @Value: `int containerId`, `ItemContainer itemContainer`) â€” fires "whenever the stack size of an Item in an ItemContainer is modified", including "Withdrawing an item from bank (triggers for both bank and player inv)". Compare `getContainerId()` against **`net.runelite.api.gameval.InventoryID`** constants: `INV = 93` (player inventory), `WORN = 94`, `BANK = 95`, `SEED_VAULT = 626`. The old enum `net.runelite.api.InventoryID` still exists but is `@Deprecated` â€” do not use it; gameval is the current convention (AGENTS.md: "Use net.runelite.api.gameval constants (ItemID, InterfaceID, ObjectID, etc.) instead of magic numbers").
- Bank open/close detection â€” current best practice per the core BankPlugin (master): `onWidgetLoaded(WidgetLoaded e)` with `e.getGroupId() == InterfaceID.BANKMAIN` sets bankOpen=true; `onWidgetClosed(WidgetClosed e)` same groupId sets false. `net.runelite.api.gameval.InterfaceID.BANKMAIN = 12`, `BANKSIDE = 15`, `INVENTORY = 149`, `BANK_DEPOSITBOX = 192` (file header: "This file is automatically generated. Do not edit."). BankPlugin uses `ScriptPostFired` only for interface-rebuild concerns (ScriptID.BANKMAIN_FINISHBUILDING, BANKMAIN_SEARCH_REFRESH, POTIONSTORE_BUILD) â€” you only need that if you redraw against the bank widget layout. **For material counting, you don't strictly need bank-open detection at all**: `ItemContainerChanged` with containerId == InventoryID.BANK (95) fires when the bank is opened and on every bank content change; cache that snapshot (and persist it via ConfigManager to survive restarts, since `client.getItemContainer(InventoryID.BANK)` is null until the bank has been opened this session).
- `ConfigChanged` (net.runelite.client.events.ConfigChanged) â€” fired by ConfigManager.setConfiguration with fields group, profile, key, oldValue, newValue; filter on `event.getGroup()`.
- `RuneScapeProfileChanged` (net.runelite.client.events) â€” "Posted when the user switches to a different RuneScape save profile" (different account login, or hopping to/from Beta/Tournament/DMM/Leagues worlds); fields `String previousProfile`, `String newProfile` (nullable). Reload RS-profile-scoped state here. `ProfileChanged` fires when the *config* profile switches.

## 4. Config interfaces
`@ConfigGroup(String value)` on the interface â€” value is "the key name of the config group used for storing configuration", conventionally lowercase plugin name without spaces (example: `grandexchange`). AGENTS.md: use a *specific* group name (e.g. "deadman-prices" not "deadman") and "Always provide migrations when renaming config keys or groups". `@ConfigItem` attributes: `int position() default -1`, `String keyName()`, `String name()`, `String description()`, `boolean hidden() default false`, `String warning() default ""`, `boolean secret() default false`, `String section() default ""`. `@ConfigSection` (on fields): `String name`, `String description`, `int position`, `boolean closedByDefault default false`. Also available in net.runelite.client.config: `@Range`, `@Units`, `@Alpha`, `Keybind`, `Notification`. Config interface extends `net.runelite.client.config.Config`; `default` methods supply defaults; boolean â†’ checkbox, int â†’ spinner, enum â†’ dropdown, etc. Provide the config to Guice in the plugin class:
```java
@Provides MyConfig provideConfig(ConfigManager configManager) { return configManager.getConfig(MyConfig.class); }
```

## 5. ConfigManager for hidden/arbitrary state (net.runelite.client.config.ConfigManager)
Exact signatures (master): `String getConfiguration(String groupName, String key)`; `String getConfiguration(String groupName, String profile, String key)`; `<T> T getConfiguration(String groupName, String key, Type clazz)`; `<T> T getConfiguration(String groupName, String profile, String key, Type type)`; `void setConfiguration(String groupName, String key, String value)`; `<T> void setConfiguration(String groupName, String key, T value)` (+ profile-qualified overloads); `void unsetConfiguration(String groupName, String key)`; RS-profile variants: `String getRSProfileConfiguration(String groupName, String key)`; `<T> T getRSProfileConfiguration(String groupName, String key, Type clazz)`; `<T> void setRSProfileConfiguration(String groupName, String key, T value)`; `void unsetRSProfileConfiguration(String groupName, String key)`; `<T extends Config> T getConfig(Class<T> clazz)`. Serialization via internal `objectToString/stringToObject` supports boolean, int, long, double, Color, Dimension, Point, Rectangle, Enum, Instant, Duration, Keybind, ModifierlessKeybind, WorldPoint, byte[], parameterized `Set`, and any type annotated `@ConfigSerializer(Class<? extends Serializer<?>>)`. For arbitrary structures (our planned-items list / cached bank snapshot), the common Plugin-Hub pattern is: serialize with injected Gson to a String and store via setConfiguration; hide it from the UI either by not declaring it in the Config interface at all (raw ConfigManager keys) or with `@ConfigItem(hidden = true)`. Keys are stored as `group.key`; RS-profile keys as `group.rsprofile.<profileKey>.key` (splitKey â†’ {group, profile, key}). RS-profile caveats: `getRSProfileConfiguration` returns null while no RS profile is bound (not logged in); `setRSProfileConfiguration` while logged out logs "trying to create a profile while not logged in" and does nothing â€” the rsProfileKey is assigned from account hash + world type on login (updated on AccountHashChanged/WorldChanged/PlayerChanged). So per-account state writes must happen while LOGGED_IN.

## 6. Gson
RuneLiteModule binds Gson directly: `bind(Gson.class).toInstance(RuneLiteAPI.GSON);` â€” so `@Inject Gson gson;` gives the client's shared configured instance. Review rule (AGENTS.md + actual PR feedback): "Do not create fresh Gson instances, always @Inject the client's Gson" â€” customize via `gson.newBuilder()...create()`, never `new Gson()`/`new GsonBuilder()`. Rationale: memory (each Gson instance carries adapter caches), consistent type adapters, and it's flagged in plugin-hub review. Also: do NOT add gson/guava/okhttp/guice as dependencies in build.gradle â€” they're provided transitively by `net.runelite:client`.

## 7. Threading
- `ClientThread` (net.runelite.client.callback, @Singleton): `invoke(Runnable)` â€” runs immediately if already on client thread else queues; `invoke(BooleanSupplier)` â€” "Will run r on the game thread, at an unspecified point in the future. If r returns false, r will be ran again"; `invokeLater(Runnable)` / `invokeLater(BooleanSupplier)` â€” always queued to run after current method returns, BooleanSupplier false â†’ retried later; `invokeAtTickEnd(Runnable)` â€” end of current game tick.
- Rules: all `net.runelite.api.Client` access (ItemContainer reads, ItemComposition lookups, widget reads) on the client thread; all Swing (PluginPanel updates) on the EDT via `SwingUtilities.invokeLater`. @Subscribe game-event handlers already run on the client thread. From an OkHttp callback (or any worker thread) use `clientThread.invoke()` to touch the client. Never `Thread.sleep()`; never block in startUp/shutDown; blocking I/O off the client thread.
- `@Schedule` (net.runelite.client.task.Schedule): attributes `long period`, `ChronoUnit unit`, `boolean asynchronous() default false`. Scheduler.tick() is driven from Hooks' per-frame callback on the client thread, gated to roughly once per game tick (CHECK = RSTimeUnit.GAME_TICKS duration) â€” so asynchronous=false @Schedule methods run **on the client thread** with ~600ms granularity; asynchronous=true submits to the injected singleton ScheduledExecutorService. @Schedule methods on the plugin class are auto-registered while the plugin is active.

## 8. Plugin Hub submission + review (plugin-hub README, Plugin-Hub-Review wiki, example-plugin AGENTS.md)
Submission: fork runelite/plugin-hub, add `plugins/<your-plugin>` file containing `repository=<https clone url>\ncommit=<40-char sha>`, PR it; CI (`net.runelite.pluginhub.packager.Packager`) must pass. Repo needs `runelite-plugin.properties` (displayName, author, description, tags, plugins=FQCN, optional version, build=standard|gradle â€” "standard" replaces your build files and gets expedited review), optional `icon.png` (max 48x72), README.md, BSD 2-Clause LICENSE. `runeLiteVersion` must be `'latest.release'`. Non-transitive dependencies require Gradle dependency verification (cryptographic hashes). Since April 2026 an AI review bot auto-approves simple updates; humans review the rest. Review scope: security (no reflection â€” explicitly prohibited; no JNI/JNA/Unsafe/native; no Process/ProcessBuilder; no dynamic classloading or code download; no Java serialization) and Jagex-rule compliance ("If it is difficult for us to ensure the plugin isn't against the rules we will not merge it").

Technical review feedback that rejects/blocks PRs (from AGENTS.md, which is the distilled reviewer feedback doc): new Gson()/hardcoded Gson; magic numbers instead of gameval constants; log.info spam (use log.debug; INFO only for one-time startup/shutdown); scanning the whole scene per frame instead of tracking spawn events; heavy computation in Overlay.render() (runs every frame); files outside RuneLite.RUNELITE_DIR (use a plugin subdir of ~/.runelite); java.awt.Desktop instead of LinkBrowser; HTTP via anything but injected OkHttpClient (and use enqueue(), never execute() on client thread); leftover template placeholders / META-INF/services file / committed build artifacts; unoptimized PNGs (memory = w*h*4); missing shutDown cleanup of subscriptions/listeners/overlays; reformatting mixed into feature commits; third-party-server features not disabled by default (must warn "This feature submits your IP address to a 3rd-party server not controlled or verified by RuneLite developers"). Target Java 11, Lombok 1.18.30, `compileOnly 'net.runelite:client:latest.release'` from repo `https://repo.runelite.net`, test-run main class pattern: `ExternalPluginManager.loadBuiltin(MyPlugin.class); RuneLite.main(args);` launched via `./gradlew run` with `--developer-mode --debug -ea`.

Content-policy notes relevant to us: a material/checklist planner is well within policy (no combat assistance, no input injection, no menu changes needed). Avoid adding menu entries that send server actions and avoid any autotyping.

## Key facts
- @PluginDescriptor fields on master: name (required), configName="", description="", tags={} (lowercase, no spaces), conflicts={}, enabledByDefault=true (javadoc: Plugin-Hub plugins should always leave this true), hidden=false, developerPlugin=false, loadInSafeMode=true (package net.runelite.client.plugins).
- Plugin base class: public abstract class Plugin implements Module, with protected void startUp() throws Exception, protected void shutDown() throws Exception, public void resetConfiguration(); EventBus auto-registers the plugin instance around startUp/shutDown, so only extra objects (overlays, nav buttons, non-plugin subscribers) need manual register/unregister.
- Sidebar panel pattern: NavigationButton.builder().tooltip(String).icon(BufferedImage).priority(int).panel(PluginPanel).build(); clientToolbar.addNavigation(btn) in startUp, clientToolbar.removeNavigation(btn) in shutDown; add/removeNavigation internally use SwingUtilities.invokeLater so they are thread-safe; overlayManager.add/remove likewise in startUp/shutDown.
- @Subscribe (net.runelite.client.eventbus.Subscribe) has one attribute: float priority() default 0, higher runs first; subscriber methods MUST be non-static void with exactly one concrete-class parameter and be named on+EventClassName (enforced via reflection at register time, dispatched via LambdaMetafactory).
- EventBus API: synchronized void register(Object), synchronized <T> Subscriber register(Class<T>, Consumer<T>, float priority), synchronized void unregister(Object|Subscriber), void post(Object). Game events are dispatched on the client thread.
- Bank detection best practice (verified from core BankPlugin on master): WidgetLoaded with getGroupId()==InterfaceID.BANKMAIN (gameval value 12) for open, WidgetClosed same id for close; ItemContainerChanged with getContainerId()==InventoryID.BANK for contents. ScriptPostFired (ScriptID.BANKMAIN_FINISHBUILDING / BANKMAIN_SEARCH_REFRESH) is only used when re-rendering against the rebuilt bank widget layout â€” not needed for pure content tracking.
- Current container-ID constants are net.runelite.api.gameval.InventoryID (auto-generated class): INV=93 (player inventory), WORN=94, BANK=95, SEED_VAULT=626. The old enum net.runelite.api.InventoryID still exists but is @Deprecated â€” reviewers expect gameval constants (ItemID, InventoryID, InterfaceID, ObjectID) instead of magic numbers or deprecated classes.
- ItemContainerChanged (@Value: int containerId, ItemContainer itemContainer) fires whenever a stack size in an ItemContainer changes, including bank withdraw/deposit (fires for both bank and inventory containers); the BANK container first populates when the player opens the bank, so client.getItemContainer(InventoryID.BANK) is null until then â€” persist a bank snapshot via ConfigManager if totals must survive restarts.
- ConfigManager signatures on master: String getConfiguration(String group, String key); <T> T getConfiguration(String group, String key, Type clazz); void setConfiguration(String group, String key, String value); <T> void setConfiguration(String group, String key, T value); void unsetConfiguration(String group, String key); String getRSProfileConfiguration(String group, String key); <T> T getRSProfileConfiguration(String group, String key, Type clazz); <T> void setRSProfileConfiguration(String group, String key, T value); void unsetRSProfileConfiguration(String group, String key); <T extends Config> T getConfig(Class<T> clazz).
- ConfigManager serialization natively handles boolean/int/long/double/Color/Dimension/Point/Rectangle/Enum/Instant/Duration/Keybind/WorldPoint/byte[]/parameterized Set and @ConfigSerializer(Serializer.class)-annotated types; anything else should be Gson-serialized to a String by the plugin. Keys stored as group.key; RS-profile keys as group.rsprofile.<profileKey>.key.
- RS-profile caveats: getRSProfileConfiguration returns null while no RS profile is bound (logged out); setRSProfileConfiguration while logged out logs 'trying to create a profile while not logged in' and silently does nothing; the profile key updates on account hash/world/player changes. RuneScapeProfileChanged (net.runelite.client.events) posts on profile switches (different account, or Beta/Tournament/DMM/Leagues world hop) with previousProfile/newProfile.
- setConfiguration posts a ConfigChanged event (fields: group, profile, key, oldValue, newValue) on the EventBus â€” subscribe to onConfigChanged and filter event.getGroup() to react to settings changes.
- Gson: RuneLiteModule contains bind(Gson.class).toInstance(RuneLiteAPI.GSON). Plugin-hub review rule: 'Do not create fresh Gson instances, always @Inject the client's Gson' â€” customize via gson.newBuilder(); new Gson()/new GsonBuilder() is flagged in review. Do not declare gson/okhttp/guava as gradle deps; they come from net.runelite:client.
- ClientThread (net.runelite.client.callback, @Singleton): invoke(Runnable) runs immediately if already on client thread else queues; invoke(BooleanSupplier)/invokeLater(BooleanSupplier) re-run the task later whenever it returns false; invokeLater always defers past the current method; invokeAtTickEnd(Runnable) runs at end of current game tick. All net.runelite.api.Client access belongs on the client thread; all Swing/PluginPanel work belongs on the EDT via SwingUtilities.invokeLater; @Subscribe handlers already run on the client thread.
- @Schedule (net.runelite.client.task.Schedule): long period, ChronoUnit unit, boolean asynchronous default false. - Plugin Hub submission: PR to runelite/plugin-hub adding plugins/<id> file with repository=<https url> and commit=<40-char sha>; repo must contain runelite-plugin.properties (displayName, author, description, tags, plugins=FQCN, build=standard|gradle), BSD-2-Clause LICENSE, optional icon.png max 48x72 and README.md; runeLiteVersion='latest.release'; non-transitive deps need Gradle dependency-verification hashes; use Class.getResourceAsStream() for bundled resources.
- Hard security rules (reviewed + auto-scanned): no reflection, no JNI/JNA/Unsafe/native memory, no Process/ProcessBuilder, no dynamic classloading or downloading code, no Java serialization; Java 11 target required. - Common technical review feedback (from runelite/example-plugin AGENTS.md â€” the canonical best-practices doc): log.debug for frequent output (client runs at INFO); never Thread.sleep or block in startUp/shutDown; no per-frame scene scans (use spawn events); minimize work in Overlay.render(); files only under RuneLite.RUNELITE_DIR in a plugin subdir; LinkBrowser not java.awt.Desktop; @Inject OkHttpClient with enqueue(); clientThread.invoke() when touching the client from okhttp callbacks; clean up subscriptions/listeners/overlays in shutDown; remove template leftovers and META-INF/services file; optimize PNGs; migrations when renaming config keys/groups; 3rd-party-server features off by default with the exact IP-disclosure warning string; separate reformatting commits.

## Risks
- net.runelite.api.InventoryID (enum) and net.runelite.api.widgets.InterfaceID/ComponentID/WidgetID are deprecated; only net.runelite.api.gameval.* is current. Code samples older than ~2024 (most blog posts and many hub plugins) use the deprecated forms â€” do not copy them.
- gameval InventoryID/InterfaceID are auto-generated 'do not edit' files that track game updates; constant NAMES (INV vs INVENTORY, WORN vs EQUIPMENT) differ from the deprecated enums, which trips up memory-based coding. Verified values: INV=93, WORN=94, BANK=95, SEED_VAULT=626, InterfaceID.BANKMAIN=12.
- client.getItemContainer(InventoryID.BANK) is null until the player opens the bank in the current session â€” a bank-inclusive materials count must persist the last snapshot (ConfigManager + Gson) and clearly mark staleness, or show 'open your bank' state.
- setRSProfileConfiguration silently no-ops (warn log only) when not logged in, and getRSProfileConfiguration returns null â€” guard all per-account persistence behind GameState.LOGGED_IN and handle RuneScapeProfileChanged to avoid cross-account bleed.
- @Schedule synchronous tasks execute on the client thread with ~600ms granularity (driven from Hooks draw callback) â€” fine for recomputes, but heavy work there stalls the game; asynchronous=true runs on a shared single-thread ScheduledExecutorService shared with other client tasks.
- EventBus enforces the on+EventClassName naming convention at registration â€” a mis-named @Subscribe method throws at plugin start, not compile time.
- Plugin Hub review since April 2026 includes an automated AI review bot plus human reviewers; automated scanning rejects reflection, native code, Process usage, serialization, and fresh Gson instances. 'standard' build mode gets expedited review; custom gradle build gets slower review.
- ConfigManager method list and RuneLiteModule details were extracted via summarizing fetches of the raw master sources (not read line-by-line); signatures matched across two independent fetches, but re-verify exact overloads in IDE once net.runelite:client:latest.release is on the classpath.
- runeLiteVersion must be 'latest.release' and the hub rebuilds against current client â€” deprecated-API usage that still compiles today can break on any client release; CI failures on existing hub plugins after API bumps are common.
- The wiki page 'Creating plugin config panels' is explicitly incomplete ('Somebody write this page properly!'); the authoritative best-practices document is now AGENTS.md in runelite/example-plugin â€” treat it as the review checklist.
- loadInSafeMode default true and enabledByDefault must stay true for hub plugins; setting enabledByDefault=false is called out in the annotation javadoc as confusing for hub users.
